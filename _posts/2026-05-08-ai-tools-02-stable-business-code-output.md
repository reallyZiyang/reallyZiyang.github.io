很多游戏功能，本质上都是在现有框架下做常规业务开发，比如宠物系统、宝石系统、活动副本、商店系统和任务系统。这些功能不一定有多难，但规则很多。

代码要放在哪，数据怎么刷新，UI 怎么调用，协议怎么接，Command 能不能写业务逻辑，Model 能不能发请求，这些都有项目自己的习惯。所以让 AI 稳定产出业务代码，重点不是让它自由发挥，而是让它按项目规则写。

我现在更倾向于把这件事拆成几部分：开发规范、项目结构、业务代码规范和 Agent 角色。这些东西看起来像文档，但对 AI 很关键，因为它们能减少 AI 的选择空间。选择空间越少，结果就越稳定。

## 开发规范

开发规范解决的是代码风格问题，比如字段怎么命名、文件怎么组织、类成员怎么排序、方法要不要拆小、注释写到什么程度、partial 什么时候能用。

这些规则对人来说可能只是习惯。但对 AI 来说，如果不写清楚，它很容易把别的项目风格带进来。最后代码也许能跑，但看起来不像当前项目的代码。

这种问题很隐蔽。它不一定马上报错，但会让项目风格越来越乱。所以开发规范的意义不是追求形式，而是让 AI 少猜一点。

## 项目结构

项目结构解决的是代码落点问题。常规业务开发很少是从零建一套东西，更多是在已有框架里补功能。

比如一个玩法系统，可能会拆成 Data、Interface、System、Command、Proto、UI。如果 AI 不知道这些层的职责，就很容易写错位置。

常见问题包括：把数据逻辑写进 UI，把网络请求写进 Model，把业务逻辑写进 Command，把协议处理散落到不同文件。这些都不是语法问题，而是工程结构问题。

所以需要提前告诉 AI：Model 只存数据，System 负责业务和网络逻辑，Command 只做薄封装，UI 只消费数据和发起操作，Proto 文件集中处理协议。这些边界清楚以后，AI 才知道代码应该落在哪里。

## 业务代码规范

业务代码规范解决的是“这个项目的功能应该怎么接”。

以常规玩法系统为例，比较稳定的模式是：Data 定义 Bindable 数据，Interface 声明系统能力，Command 封装 UI 操作，System 实现业务逻辑，Proto 处理 C2S 和 S2C。

这里最重要的是职责边界。比如 Command 只是薄层，不应该写业务逻辑。它的职责就是把 UI 操作转发给 System，真正的业务逻辑应该放在 System。

再比如网络请求成功后，大多数情况下不应该直接用回包写 Model，而是等 S2C 推送刷新状态。这些规则不是通用 C# 知识，而是项目自己的业务约定。

如果不告诉 AI，它可能会写出“能编译，但不符合项目工作流”的代码。所以业务代码规范的价值，是把项目经验显式写出来，让 AI 不只是会写代码，而是会按这个项目的方式写代码。

## Agent 角色

Agent 角色这块后面可以单独写一篇，这里先简单说一下。

常规业务开发不是所有任务都属于同一层。有些任务主要是 System，有些任务主要是 UI，有些任务是 UI + System，有些任务是战斗链路，有些任务是渲染表现。

如果都交给一个泛化 Agent，结果很容易漂。更稳定的方式是按职责拆角色：玩法系统工程师处理 System、Command、Data、Proto；玩法界面工程师处理 View、Binding、UI 刷新和交互；战斗玩法工程师处理 Level、BattleDriver、BattleEvent、战报回放；图形渲染工程师处理 Shader、URP、Spine、UI 特效；总控 Agent 负责判断任务类型、拆分任务和补齐上下文。

Agent 角色不是为了让提示词变复杂，它的核心作用是减少职责混乱。当任务明确是 System-only，就不要让 UI 角色去猜；当任务同时涉及 UI 和 System，就应该拆开，而不是让一个 Agent 在两个层之间来回摇摆。

## 当前阶段的分工

在当前阶段，我不太建议把验收和审核完全交给 Agent。Agent 可以根据规范产出代码，也可以做一些基础检查，但它还不具备稳定判断业务结果是否真正正确的能力。

游戏业务里很多判断依赖实际运行效果、策划预期、项目历史规则和开发者经验。这些东西不是只看代码就能完全判断的。

所以更合理的分工是：Agent 负责按规范产出，开发者负责审核和验收。这并不是否定 Agent 的能力，而是现阶段更稳的协作方式。

## 总结

常规业务开发想让 AI 稳定产出，关键不是写一个很长的 prompt，而是把项目规则提前固定下来。

至少要有开发规范、项目结构说明、业务代码规范、Agent 角色分工和固定任务输入模板。这些内容固定以后，AI 才更容易从“会写代码”，变成“会按当前项目的方式写业务代码”。
