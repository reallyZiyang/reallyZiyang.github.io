## 先给结论

很多游戏功能都是在现有框架下进行的常规业务开发。

例如：

- 宠物系统
- 宝石系统
- 活动副本
- 商店系统
- 任务系统

这类需求通常不是技术难点，而是工程规则很多。

它们需要遵守既有项目结构、命名规范、数据流、网络协议、UI 调用方式和系统分层。

因此，想让 AI 稳定产出业务代码，重点不是让它自由发挥，而是提前把规则固定下来。

可以概括为：

```text
开发规范
-> 项目结构
-> 业务代码规范
-> Agent 角色
-> 稳定产出
```

## 开发规范

开发规范解决的是“代码应该长什么样”。

例如：

- 命名规则
- 文件组织
- 类成员顺序
- 方法长度
- 注释原则
- using 排序
- partial 使用边界

这些规则看起来琐碎，但对 AI 很重要。

因为 AI 写代码时很容易混用不同项目的风格。

如果没有明确规范，它可能写出能运行但不像当前项目的代码。

例如字段命名、方法拆分、注释风格、类文件组织都可能和项目已有代码不一致。

所以开发规范的价值不是让代码更“漂亮”，而是减少 AI 的选择空间。

选择空间越小，产出越稳定。

## 项目结构

项目结构解决的是“代码应该放在哪里”。

对于游戏项目来说，很多业务开发不是从零开始。

它通常需要接入现有目录结构。

例如一个玩法系统可能会涉及：

```text
Data
Interface
System
UI
Command
Proto
```

如果 AI 不知道项目结构，它很容易把代码写到错误位置。

例如：

- 把数据逻辑写进 UI
- 把网络请求写进 Model
- 把业务逻辑写进 Command
- 把协议处理分散到多个文件

这些问题不一定立刻报错，但会破坏项目长期结构。

因此，项目结构说明要让 AI 明确每一层的职责。

例如：

```text
Model 只存数据
System 实现业务和网络逻辑
Command 只做薄封装
UI 只消费数据和发起操作
Proto 分部文件集中处理协议
```

当这些位置固定下来后，AI 就不需要猜“这段代码应该放哪”。

## 业务代码规范

业务代码规范解决的是“这类功能应该怎么写”。

例如常规玩法系统通常会遵循固定模式：

```text
Data 定义 Bindable 数据
Interface 声明系统能力
Command 封装 UI 操作
System 实现业务逻辑
Proto 处理 C2S 和 S2C
```

这里最关键的是职责边界。

例如 Command 不应该包含业务逻辑。

它只负责把 UI 操作转发给 System。

System 才是业务和网络逻辑的实现位置。

再比如主动请求成功后，大多数情况下不应该直接用回包写 Model，而是等待 S2C 推送刷新状态。

这类规则非常适合写进 AI 规范。

因为它们不是通用 C# 知识，而是项目业务约定。

AI 如果不知道这些约定，就容易写出“语法正确但工作流错误”的代码。

因此，业务代码规范的作用是把项目经验显式化。

让 AI 不只是会写代码，而是按当前项目的方式写代码。

## Agent 角色

Agent 角色解决的是“让谁来做这件事”。

常规业务开发并不是所有问题都属于同一层。

有些任务主要改 System。

有些任务主要改 UI。

有些任务跨 UI 和 System。

有些任务属于战斗链路或渲染表现。

如果所有任务都交给同一个泛化 Agent，稳定性会下降。

更稳定的方式是按职责拆分角色。

例如：

- 玩法系统工程师：处理 System、Command、Data、Proto
- 玩法界面工程师：处理 View、Binding、UI 刷新和交互
- 战斗玩法工程师：处理 Level、BattleDriver、BattleEvent、战报回放
- 图形渲染工程师：处理 Shader、URP、Spine、UI 特效
- 总控 Agent：负责判断任务归类、拆分任务和补齐上下文

这部分后面可以单独展开。

这里只需要明确一点：

```text
Agent 角色不是为了让提示词更复杂，而是为了减少职责混乱
```

当一个任务明确属于 System-only，就不要让 UI 角色去猜。

当一个任务同时涉及 UI 和 System，就应该拆开，而不是让单个 Agent 在两个层之间来回漂移。

## 稳定产出的关键

让 AI 稳定产出业务代码，关键不是一次性写出很长的需求描述。

更重要的是让它拿到稳定的工作流。

可以理解为：

```text
规范告诉 AI 怎么写
结构告诉 AI 写在哪
业务规则告诉 AI 怎么接入现有系统
Agent 角色告诉 AI 当前任务属于谁
```

在当前阶段，不建议把验收和审核完全交给 Agent。

Agent 可以根据规范产出代码，也可以做一些基础检查。

但它还不具备稳定判断业务结果是否真正正确的能力。

尤其是游戏业务开发里，很多判断依赖项目经验、实际运行效果和策划预期。

因此，更合理的分工是：

```text
Agent 负责按规范产出
开发者负责审核和验收
```

## 总结

常规业务开发的 AI 工作流，本质上是在降低不确定性。

对于宠物、宝石、活动副本这类功能，真正影响稳定性的通常不是某段代码有多难，而是 AI 是否理解项目规则。

因此，更有效的做法是提前准备：

- 开发规范
- 项目结构说明
- 业务代码规范
- Agent 角色分工
- 明确的任务输入模板

当这些内容固定下来后，AI 才更容易从“会写代码”变成“会按当前项目的方式写业务代码”。
