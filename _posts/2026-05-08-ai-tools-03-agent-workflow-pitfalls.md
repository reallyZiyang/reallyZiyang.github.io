实际用 AI 写业务代码时，最麻烦的不是它完全不会写。更常见的问题是：它在错误的上下文里写，在错误的边界里查，或者用错误的角色理解任务。

一开始我基本都是人工补救。比如每次都手动补一堆项目规范、代码示例、任务需求、相关目录、不要做什么、输出格式。这样确实会让结果好一点，但补久了以后会发现，这些东西其实都是可预测的。既然是可预测的，就不应该每次靠人临时补，更合理的方式是把它们沉淀成 Agent 工作流。

## 第一个坑：Agent 不了解项目

AI 写业务代码最常见的问题，就是它不了解项目。它可能写得很像那么回事，但一看就不是这个项目里的代码。

比如命名风格不对、文件放错目录、业务逻辑写错层、没按现有 System 模式写、没按项目的数据刷新链路实现。这种代码有时候甚至能编译，但它会让后续维护变得很别扭。

最开始的解决方式，就是每次给它塞上下文：这是项目结构，这是开发规范，这是一个类似模块，这是任务需求，这是不要改的地方。问题是成本很高，有时候只是一个很小的只读问题，也要让它先读一大堆背景。如果每次都这样，光上下文准备和阅读就消耗很多时间。

后来我更倾向于把这些固定内容写进项目规范和角色说明里，让 Agent 一开始就知道这个项目怎么组织代码、这个角色应该看哪里、哪些目录是重点、哪些东西不能随便改。这样每次提需求时，就不用从零介绍项目。

## 第二个坑：需求不清晰它也会硬做

很多人以为需求不清楚时，AI 会主动问，实际不一定。有时候你只给一句很模糊的话，它也会直接开始执行。

缺的信息怎么办？它自己补。而这个“补”，很多时候就是脑补。

比如“帮我加一个宝石功能”，这句话缺的信息太多了：加到哪个模块，是 UI 还是 System，要不要接协议，数据从哪里来，有没有参考功能，要不要最小改动。如果这些都没说，Agent 也可能继续往下做，最后结果就很容易跑偏。

最开始的解决方式，是自己每次都把需求写得很细。但这很累，因为你不只是在提需求，还要不断检查自己有没有漏掉什么。后来我觉得这件事应该模板化，至少把需求固定成几个基本字段：目标、范围、现象或期望行为、约束、完成后由开发者如何确认。

模板不是为了让需求看起来正式，它的作用是减少遗漏。

## 第三个坑：它会一路发散

还有一个很常见的问题：Agent 太会顺着线索跑了。你让它参考一个文件，它可能会继续看这个文件引用的其他文件，然后再看其他文件的引用，再然后搜索整个项目。有时候甚至还会联网搜索，或者去翻完整 git 修改记录。

最后任务越来越慢，上下文越来越乱，甚至卡住。

最开始我会手动限制它：只看这个目录，只看这几个文件，不要搜索其他地方。但限制太死也有问题，有些关键依赖确实不在这个目录里，每次任务的引用关系也不一样。

所以更合理的方式不是简单说“只能看哪里”，而是定义探索边界。比如种子文件是优先看的几个直接相关文件，直接依赖是允许从种子文件再补读的一跳依赖，搜索默认不允许，真需要时只允许一次限定范围搜索，超过边界还缺关键事实就停止回报。

这比“随便看”和“完全不准看”都稳定。它给 Agent 留了必要的探索空间，但不会让它无限扩散。

## 第四个坑：口语输入太不稳定

平时和 AI 说话很容易口语化。但口语化输入有一个问题：每次说法不同，AI 理解也可能不同。同一个需求，今天这么说，明天换个说法，最后产出的代码结构可能就变了。

最开始的解决方式，是自己每次都尽量按同一套格式写。还会补一句：先列已确认事实，再列待定位项，再给实现计划，最后只汇报关键结果。这当然有效，但如果每次都靠人记住这些格式，长期还是不稳定。

所以更适合放进 Agent 工作流里。用户可以继续用比较自然的方式提需求，但中间需要有一层把口语需求整理成稳定任务输入。

## 总控和分流

这也是为什么需要总控 Agent。

如果没有总控，用户的一句话需求会直接交给某个执行 Agent。问题是这句话可能还没有明确属于哪一层：可能是 System，可能是 UI，也可能是 UI + System，甚至可能只是需要先做只读分析。

总控 Agent 的作用不是自己把所有事情都做完，而是先把任务分清楚。它需要根据需求和少量项目上下文，把任务分成几类：System-only、UI-only、UI+System、战斗链路、渲染问题，或者暂时不确定。

分流之后，任务再交给对应的专业 Agent。比如主要改 Data、Command、System、Proto，就交给玩法系统工程师；主要改 View、Binding、列表刷新，就交给玩法界面工程师；涉及 Level、BattleDriver、BattleEvent，就交给战斗玩法工程师。

这个流程大概是：

```text
用户原始需求
-> 总控 Agent 判断任务类型
-> 总控补齐目标、范围、已知事实和约束
-> 总控指定种子文件和探索边界
-> 分流给对应专业 Agent
-> 专业 Agent 执行具体任务
```

这样做的好处是，子 Agent 收到的不是一句口语化需求，而是一份更稳定的任务说明。它知道自己是谁、该看哪里、能改哪里、哪些地方不应该碰。

总控和专业 Agent 的分工也很重要。总控负责整理和分流，专业 Agent 负责执行。这样既不会让一个泛化 Agent 在所有层之间乱跑，也不会让每个专业 Agent 都从零理解用户需求。

## 为什么要做成工作流

这些坑刚开始都可以靠人工解决。项目不了解，就手动塞上下文；需求不清晰，就手动补细节；探索发散，就手动限制范围；输出不稳定，就手动规定格式。

但这些事情做多以后，会发现它们本身都很机械。既然机械，就应该交给工作流，而不是每次靠人临时发挥。

Agent 工作流要解决的不是“让提示词更长”。它解决的是固定项目规范、固定任务输入、固定探索边界、固定角色分工、固定输出格式。这样 AI 才不会每次都重新理解项目，也不会在模糊需求里自由发挥。

## 总结

AI 生成业务代码的稳定性，不只取决于模型能力，很多时候更取决于工作流有没有把它约束住。

它应该看正确的上下文，停在正确的边界，扮演正确的角色，接收稳定的任务格式，并且在事实不足时停止，而不是脑补。

一开始这些事情可以靠开发者手动补。但长期来看，手动补不稳定，也很消耗精力。更好的方式是把这些内容沉淀成 Agent 工作流。这样开发者只需要提出目标，工作流负责补齐规范、边界和角色分工。
