## 先给结论

GameContext 组织模块的意义，是把客户端中的不同职责拆开。

可以概括为四类：

```text
Model：数据容器
System：系统服务
Command：一次性行为
Query：查询行为
```

这套拆分的重点不是为了增加概念，而是为了避免所有逻辑都堆在 UI、Manager 或单例里。

当模块都通过 Context 组织后，客户端代码可以形成更清晰的关系：

```text
数据放在 Model
能力放在 System
行为通过 Command 触发
查询通过 Query 表达
模块统一从 Context 获取
```

## 解决什么问题

中大型客户端最容易出现的问题，是模块之间的关系越来越乱。

常见情况包括：

- UI 直接修改数据
- UI 直接调用多个系统
- 系统之间互相持有具体实现
- Manager 越写越大
- 单例越来越多
- 初始化顺序不清晰
- 一次性流程散落在按钮回调里

这些问题短期内不一定明显，但项目越大，维护成本越高。

例如一个按钮点击后，可能需要读数据、判断条件、发请求、打开界面、刷新红点。如果这些逻辑都写在 UI 里，UI 就会同时承担表现、业务判断和流程控制。

Context 的作用就是把这些职责拆开：

```text
UI 只负责交互和展示
Model 负责保存状态
System 负责提供能力
Command 负责表达一次行为
Query 负责返回查询结果
```

这样做可以让模块关系更稳定，也能减少跨系统直接引用。

## Model：数据容器

Model 的定位是保存数据状态。

它更像一个数据容器，而不是业务流程执行者。

适合放在 Model 里的内容包括：

- 当前登录状态
- 玩家基础数据
- 系统解锁状态
- 本地缓存数据
- 可被多个系统读取的运行时状态

Model 不应该承担太多流程逻辑。

如果 Model 既保存数据，又负责请求、跳转、弹窗、播放动画，职责就会变得混乱。

更稳定的做法是：

```text
Model 负责保存“是什么”
System 和 Command 负责处理“做什么”
```

## System：系统服务

System 的定位是提供一类稳定能力。

它通常表示一个长期存在的服务，例如：

- 网络服务
- UI 服务
- 资源服务
- 导航服务
- 红点服务
- 弹窗服务
- 配置服务

System 和 Model 的区别在于：Model 更偏状态，System 更偏能力。

例如红点模块中，红点状态可以保存在数据结构里，但红点的注册、刷新、聚合、绑定等能力更适合由 System 提供。

可以概括为：

```text
Model 是状态
System 是能力
```

System 的好处是让外部调用依赖稳定接口，而不是依赖具体实现细节。

## Command：一次性行为

Command 的定位是表达一次行为。

它适合承载“点击按钮后要做的一串动作”。

例如：

```text
领取奖励
-> 判断条件
-> 发送请求
-> 更新数据
-> 打开结果界面
-> 刷新相关状态
```

如果这类逻辑直接写在 UI 中，UI 会迅速膨胀。

拆成 Command 后，UI 只需要表达“我要执行这个行为”，具体流程由 Command 组织。

Command 的价值在于：

- 把一次性流程从 UI 中移走
- 让行为可以被复用
- 让流程入口更清晰
- 让行为依赖通过 Context 获取

可以理解为：

```text
UI 触发 Command
Command 组织一次行为
Command 内部调用需要的 System 和 Model
```

## Query：查询行为

Query 的定位是表达一次查询。

它适合处理那些需要组合多个数据来源的只读逻辑。

例如：

```text
某个按钮是否可点击
某个系统是否可进入
某个红点是否应该显示
某个资源是否足够
某个奖励是否可领取
```

这些逻辑如果直接写在 UI 里，UI 会知道太多数据细节。

如果写在某个具体 System 里，又可能让 System 之间产生额外依赖。

Query 可以作为一种中间层，把“如何计算这个结果”封装起来。

它和 Command 的区别是：

```text
Command 负责做一件事
Query 负责问一个结果
```

## Context 的核心价值

Context 的价值不是替代所有架构模式，而是提供一个统一的模块组织入口。

它解决的是：

```text
模块在哪里注册
模块什么时候初始化
模块之间如何访问
一次行为如何触发
查询结果如何获得
```

在没有 Context 的情况下，这些问题很容易散落到各种单例、UI 脚本、Manager 和场景对象里。

有了 Context 后，模块之间的关系可以被约束在一套统一规则里。

## 总结

GameContext 的核心意义，是把客户端中的不同职责拆开。

可以用一句话概括：

> Model 存数据，System 提供能力，Command 表达行为，Query 表达查询，Context 负责统一组织和访问。

这种拆分能让 UI 更轻、系统边界更清楚，也能让一次性行为和查询逻辑从表现层中独立出来。

对于游戏客户端来说，这种结构最大的价值不是“看起来更架构化”，而是让项目规模变大后，模块之间仍然有比较清晰的协作边界。
