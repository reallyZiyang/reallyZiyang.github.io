## 先给结论

Buff 是战斗系统中的持续状态，用来描述一段时间内存在的规则，并在生命周期中的特定节点触发 Effect。

Buff 的字段扩展本身并不复杂。真正容易影响系统复杂度的，是覆盖、叠层、刷新、驱散、回滚等生命周期规则。

可以概括为：

> Buff 的难点不在于实现某个效果，而在于生命周期规则是否清晰。

## Buff 的定位

在前面的拆分中，Effect 是一次性的效果执行单元，而 Buff 是持续存在的状态。

两者的边界可以这样理解：

```text
Effect：执行一次，产生一个具体结果
Buff：持续存在，在特定生命周期节点触发 Effect
```

例如中毒效果可以拆成：

```text
AddBuffEffect
  -> 给目标添加 PoisonBuff
  -> PoisonBuff 每隔一段时间触发 DamageEffect
```

这里 AddBuffEffect 只执行一次，PoisonBuff 才是真正持续存在的状态。

## 基础数据

Buff 通常会包含一些基础数据，用来描述它是谁添加的、属于谁、当前状态如何。

常见数据包括：

- 来源
- 拥有者
- 堆叠层数
- 最大层数
- 标签
- 是否可驱散

这些数据通常用于后续规则判断。

例如同一个中毒 Buff，如果来源不同，可能需要判断它们是互相覆盖、独立共存，还是按来源分别计算层数。

## 生命周期字段

Buff 也会包含一些和生命周期相关的字段。

常见字段包括：

- 持续时间
- 覆盖规则
- 触发间隔
- 添加时触发的 Effect
- 间隔时触发的 Effect
- 移除时触发的 Effect

这些字段本身比较直观。

例如：

```text
需要添加时触发效果
-> 配置 OnAddEffects

需要间隔触发效果
-> 配置 Interval 和 OnTickEffects

需要移除时触发效果
-> 配置 OnRemoveEffects
```

从字段层面看，Buff 似乎只是一些配置的堆叠。需要新增一种触发时机，就增加对应字段；需要支持一种参数，就增加对应数据。

但这种简单通常只停留在字段层面。

## 难点从哪里开始出现

当 Buff 进入实际设计和开发时，复杂度通常会从生命周期规则中显现。

典型问题包括：

- 同类 Buff 的覆盖规则
- 堆叠层数和覆盖的关系
- 不同来源的同名 Buff 是否堆叠
- 属性修改如何回滚
- 覆盖时剩余时间如何计算
- Buff 能否被驱散
- 驱散时是否触发移除效果
- 移除时添加的其他 Buff 如何处理

这些问题本质上不是“字段够不够”的问题，而是“规则语义是否明确”的问题。

## 覆盖规则是生命周期的入口

覆盖规则经常是 Buff 系统中最先暴露复杂度的地方。

当一个新的 Buff 被添加到目标身上时，系统不能只是简单地创建一个实例，还需要先判断已有 Buff 和新 Buff 的关系。

例如：

```text
请求添加 Buff
-> 判断是否已有同类 Buff
-> 根据覆盖规则决定后续行为
```

常见覆盖行为包括：

- 拒绝添加
- 替换旧 Buff
- 刷新持续时间
- 增加层数
- 独立共存
- 按来源区分共存

覆盖规则不是孤立配置。它会直接决定 Buff 的生命周期如何开始、是否重启、是否合并，以及旧 Buff 是否需要结束。

## 覆盖规则会影响后续生命周期

不同覆盖规则会带来完全不同的生命周期行为。

### 拒绝添加

```text
已有同类 Buff
-> 新 Buff 被拒绝
-> 不触发 OnAdd
-> 不创建新的生命周期
```

这种规则适合一些唯一状态，例如某些不可重复的控制、护盾或特殊状态。

### 刷新持续时间

```text
已有同类 Buff
-> 刷新持续时间
-> 是否重新触发 OnAdd 需要明确
-> Tick 计时是否重置需要明确
```

刷新时间看起来简单，但需要明确 Tick 节奏是否一起重置。

如果不提前定义，可能会出现表现上刷新了时间，但间隔触发逻辑仍然沿用旧计时的问题。

### 替换旧 Buff

```text
已有同类 Buff
-> 移除旧 Buff
-> 是否触发旧 Buff 的 OnRemove 需要明确
-> 添加新 Buff
-> 触发新 Buff 的 OnAdd
```

替换规则需要特别注意 OnRemove。

如果旧 Buff 移除时会触发其他效果，例如爆炸、回血、返还护盾，那么替换行为是否应该触发这些效果必须提前定义。

### 增加层数

```text
已有同类 Buff
-> 层数 +1
-> 是否刷新持续时间需要明确
-> 是否触发 OnStack 需要明确
```

叠层是 Buff 中很常见的设计，但也容易和持续时间产生关系。

常见问题包括：

- 叠层时是否刷新持续时间
- 达到最大层数后继续添加如何处理
- 每层是否独立计时
- 掉层时是否触发移除逻辑
- 层数变化是否触发额外 Effect

### 独立共存

```text
已有同类 Buff
-> 创建新的 Buff 实例
-> 每个 Buff 独立计时
-> 每个 Buff 独立 Tick
```

独立共存适合一些按来源或实例分别计算的效果。

例如多个敌人分别给玩家施加中毒效果，如果设计上要求每个来源独立计算，就需要允许同名 Buff 共存。

## 移除原因也属于生命周期规则

Buff 被移除并不只有一种情况。

常见移除原因包括：

- 持续时间结束
- 被驱散
- 被替换
- 单位死亡
- 切场景清理
- 手动移除

不同移除原因不一定都应该触发相同逻辑。

例如一个 Buff 在自然结束时触发爆炸效果，但在单位死亡清理时可能不应该触发。

因此 OnRemove 不应该只是简单地“移除时必定触发”，而应该结合移除原因做规则判断。

## 生命周期流程

一个比较完整的 Buff 生命周期可以抽象为：

```text
请求添加 Buff
-> 判断覆盖规则
-> 决定创建、拒绝、刷新、替换、叠层或共存
-> 触发 OnAdd
-> 开始计时
-> 按间隔触发 OnTick
-> 持续时间结束 / 被驱散 / 被替换 / 被清理
-> 根据移除原因决定是否触发 OnRemove
-> 处理必要的清理逻辑
-> Buff 销毁
```

从这个流程可以看出，覆盖规则只是生命周期开始时的分支点。

它后面还会影响持续时间、Tick 节奏、层数变化、移除逻辑和属性回滚。

## 总结

Buff 系统表面上只是一些字段的堆叠。

需要持续时间，就加持续时间字段；需要间隔触发，就加 Tick 字段；需要添加或移除时触发效果，就加 OnAddEffects 和 OnRemoveEffects。

但随着技能系统复杂度提高，Buff 真正难管理的部分通常不是字段，而是生命周期规则。

尤其是：

- 覆盖规则
- 层数关系
- 来源区分
- 时间刷新
- 驱散规则
- 移除原因
- 属性回滚

如果这些规则没有提前规划清楚，后续开发中很容易出现同一个 Buff 在不同场景下表现不一致的问题。

因此，Buff 系统的设计重点不只是“支持哪些字段”，而是要明确每个字段在生命周期中的语义。一个字段不仅要知道“有没有”，还要知道它在什么时候生效、什么时候重置、什么时候触发，以及在覆盖、叠层、驱散、移除等场景下如何处理。
