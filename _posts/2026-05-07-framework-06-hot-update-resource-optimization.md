## 先给结论

热更新资源优化不是把资源拆得越细越好，也不是按固定规则照抄一遍就能完成。

它更像一个持续检查和调整的过程：

```text
先按使用场景做基础分包
-> 打包后查看资源报告
-> 检查依赖和冗余
-> 根据实际加载情况调整 Bundle
-> 再次验证下载和加载表现
```

资源优化的目标是在几个成本之间取平衡：

- 下载体积
- 首包大小
- 首次进入速度
- 运行时加载成本
- 资源复用率
- 分包维护成本

因此，热更新资源优化不是单点规则，而是一套围绕 Package、Bundle、依赖和首包策略的综合设计。

## Package 和 Bundle 的区别

第 05 篇里提到，Package 解决的是资源编排问题。

可以理解为：

```text
Package 决定哪些资源什么时候下载
Bundle 决定 Package 内部资源如何组织和加载
```

Package 更偏“资源模块边界”。

例如：

- 核心资源 Package
- 商业化资源 Package
- 玩法资源 Package
- 场景资源 Package

Bundle 更偏“资源加载边界”。

例如一个角色、一个技能、一个界面、一组共享贴图，最终可能会被组织成不同 Bundle。

所以 06 主要关注的是：Package 内部的 Bundle 应该如何拆，以及首包资源应该如何优化。

## Bundle 分包目标

Bundle 分包的目标不是“拆得越细越好”，而是减少不必要的资源牵连。

一个合理的分包策略应该尽量做到：

- 加载一个角色时，不带出大量无关角色
- 加载一个技能时，不带出其他技能资源
- 打开一个系统界面时，不带出其他系统界面
- 通用贴图、Shader、材质等共享资源能够复用
- 高频资源尽量减少网络等待
- 低频资源不要挤占首包体积

如果 Bundle 太粗，加载一个资源时会带出大量无关内容。

如果 Bundle 太细，请求数量、依赖数量和管理复杂度又会上升。

因此，分包需要根据资源使用场景、生命周期、共享程度和加载时机来调整。

## 常见分包策略

### 角色资源独立 Bundle

单个角色资源适合独立成 Bundle。

例如：

```text
角色预制体
角色贴图
角色材质
角色动画
角色专属特效
```

这样加载某个角色时，不会把其他角色的资源一起带出来。

角色资源通常体积较大，且不同角色之间使用时机不同，因此独立分包更容易控制加载成本。

### 技能资源独立 Bundle

单个技能资源也适合独立成 Bundle。

例如：

```text
技能预制体
技能贴图
技能材质
技能音效
技能专属表现资源
```

技能资源和角色类似，也经常具有明显的使用边界。

一个技能不应该因为和其他技能放在同一个 Bundle 中，而在加载时带出大量无关资源。

### 特效预制体按功能分 Bundle

特效预制体可以按功能分类。

例如：

```text
技能特效
抛射物特效
界面特效
通用反馈特效
```

不同功能的特效生命周期不同。

技能特效通常和战斗技能相关，抛射物特效和飞行物相关，界面特效则只在 UI 中使用。

按功能拆分能减少跨场景、跨系统的资源牵连。

### 特效贴图和 Shader 作为共享 Bundle

特效贴图和 Shader 往往具有较强复用性。

这类资源可以独立作为共享 Bundle。

例如：

```text
通用特效贴图
通用 Shader
通用材质
公共噪声图
公共渐变图
```

共享 Bundle 的好处是减少重复打包，提高复用率。

但共享 Bundle 也有风险：如果一个共享资源频繁变化，它会影响所有依赖它的资源。

因此，共享 Bundle 更适合放稳定、复用率高、变化频率低的资源。

### 单个系统的界面资源独立 Bundle

UI 资源适合按系统拆分。

例如：

```text
某个系统的界面预制体
该系统专用图片
该系统专用图集
该系统专用动效
```

这样打开某个系统界面时，只加载这个系统需要的 UI 资源。

不同系统之间的 UI 不应该因为打在同一个 Bundle 里而互相牵连。

通用 UI 资源则可以单独放到公共 Bundle，例如通用按钮、通用字体、通用图标、通用弹窗底板等。

## 分包优化不是按本宣科

上面的策略只是初始规则，不是最终答案。

真正的资源优化需要在开发过程中不断查看打包报告和加载报告。

因为资源依赖经常比表面看到的更复杂。

例如：

```text
一个 UI 预制体可能依赖多个图集
一个角色预制体可能依赖多个动画和材质
一个技能特效可能依赖共享贴图和 Shader
一个看似独立的资源可能间接引用了公共资源
```

如果只看资源文件本身，很容易误判 Bundle 的实际加载成本。

因此，资源分包优化应该依赖报告检查：

```text
看 Bundle 里实际包含了什么
看 Bundle 之间有哪些依赖
看某个入口实际加载了哪些 Bundle
看是否有不该被带出的资源
看共享 Bundle 是否被过度依赖
```

只有结合报告，才能判断分包是否真的合理。

## 首包优化

热更新项目里，首包优化通常比单纯压缩资源更重要。

首包要解决的问题是：

```text
用户第一次安装或第一次启动时，多久能进入游戏
```

如果所有资源都走网络下载，首次进入体验会很差。

因此，首包应该包含运行所需的最小核心资源。

例如：

- 启动 UI
- 基础配置
- 基础字体
- 公共图集
- 主逻辑程序集
- 首次进入必须使用的角色、界面和基础资源

拓展资源则可以按需下载。

例如：

```text
进入某个玩法前下载玩法资源
打开商业化界面前下载商业化资源
进入大场景前下载场景资源
```

这样可以减少启动前的等待时间。

## 用空间换时间

如果项目更追求首包进入速度，可以用空间换时间。

一种实践方式是：

```text
在编辑器中正常游玩几分钟
-> 导出 YooAsset 资源加载报告
-> 分析这段流程实际使用到的 Bundle
-> 用代码记录这些 Bundle
-> 每次打包时把这些 Bundle 复制到 StreamingAssets
```

这样首轮体验中高频使用的 Bundle 会随包体一起存在。

启动或首局体验时，这些资源就不需要走网络下载。

这种方式本质上是在用包体空间换取进入速度。

它适合处理：

- 首次启动必用资源
- 首局战斗必用资源
- 新手流程必用资源
- 高频公共 UI 资源
- 基础角色和基础技能资源

不过这类策略也需要控制边界。

如果把太多 Bundle 放进 StreamingAssets，首包会变大；如果放得太少，首次体验仍然会频繁下载。

因此，应该根据实际报告来决定哪些 Bundle 进入首包，而不是凭感觉手动挑选。

## 依赖链检查

资源优化不能只看显式资源，还要看依赖链。

例如一个技能预制体本身很小，但它可能依赖：

```text
特效贴图
材质
Shader
音效
抛射物预制体
命中特效
```

如果这些依赖分布不合理，加载一个技能就可能带出一大片资源。

所以资源报告中最重要的不只是 Bundle 大小，还包括 Bundle 之间的依赖关系。

优化时需要重点检查：

- 是否有异常大的 Bundle
- 是否有过度共享的 Bundle
- 是否有明显不相关资源被打到一起
- 是否有频繁使用资源却没有进入首包
- 是否有低频资源被首包带入

## 总结

热更新资源优化的核心不是固定规则，而是持续检查和调整。

可以概括为：

```text
Package 控制资源什么时候下载
Bundle 控制资源如何组织和加载
报告检查验证分包是否合理
首包策略决定首次进入速度
```

常见初始策略是：

- 角色资源独立 Bundle
- 技能资源独立 Bundle
- 特效预制体按功能分 Bundle
- 特效贴图和 Shader 作为共享 Bundle
- 单个系统的 UI 资源独立 Bundle

但最终是否合理，必须通过报告和实际加载情况验证。

如果追求首包进入速度，可以把实际首轮流程中用到的高频 Bundle 放进 StreamingAssets，用包体空间换取启动和首局体验速度。
