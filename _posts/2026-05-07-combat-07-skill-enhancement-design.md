## 先给结论

技能强化是对已有技能进行扩展。

例如有一个技能 A：

```text
释放 1 个火球
火球命中后造成伤害
```

升级后的需求是：

```text
技能 A 释放 2 个火球
```

这个需求看起来很简单，但实现方式会直接影响后续扩展能力。

常见思路有三种：

- 替换技能
- 被动技能
- 技能属性

这三种方式都能实现“多发 1 个火球”，但它们适合的复杂度不同。

## 替换技能

最直接的做法是预先定义两个技能。

```text
技能 A：释放 1 个火球
技能 B：释放 2 个火球
```

升级后，把角色身上的技能 A 替换成技能 B。

这种方式的优点是简单直接。

技能数据是固定的，运行时也不需要额外处理强化逻辑。

但缺点也很明显：

```text
它只能支持预先定义好的技能变种
```

如果强化只是固定的一两档，这种方式没有问题。

例如：

```text
1 个火球
2 个火球
3 个火球
```

可以分别做成三个技能。

但如果强化开始变多，比如火球数量、伤害、范围、分裂、穿透、灼烧都可能变化，那么每种组合都做成独立技能就不现实。

因此，替换技能适合简单升级，不适合作为大量技能强化的底层方案。

## 被动技能

第二种做法是把强化做成被动技能。

升级后，角色获得一个被动技能。

这个被动技能监听技能 A 的释放。

当技能 A 释放时，被动技能额外释放 1 个火球。

可以抽象为：

```text
技能 A 释放 1 个火球
-> 被动技能监听到技能 A 释放
-> 被动技能额外释放 1 个火球
```

这种方式的优点是更灵活。

强化可以在运行时动态获得，也可以通过触发器组合出很多变化。

例如：

```text
释放技能 A 时额外释放火球
```

```text
每释放 3 次技能 A 后额外释放火球
```

```text
技能 A 命中后额外触发灼烧
```

但这种方式也有问题。

被动技能本身应该负责“特定条件下触发某些效果”。

如果大量技能强化都通过被动技能间接实现，那么被动技能的职责会变得模糊。

原本属于技能 A 的能力，会被拆散到其他被动技能里。

这样会带来两个问题：

- 技能过程难以追溯
- 技能表现和实际逻辑容易分散

例如玩家看到的是“技能 A 释放 2 个火球”，但实现上却是：

```text
技能 A 释放 1 个火球
被动技能额外释放 1 个火球
```

这并不是错误实现，但它是间接实现。

当强化数量变多后，排查一个技能最终为什么变成现在这样，会变得更困难。

## 技能属性

更适合参数类强化的方式，是把技能可变化的部分抽象成属性。

例如角色属性里可能已经有：

```text
hp：生命值
atk：攻击力
```

技能强化也可以定义类似的属性：

```text
add_projectile：额外抛射物数量
```

技能 A 的效果是发射火球，也就是生成抛射物。

生成抛射物前，读取当前角色身上的额外抛射物属性。

```text
最终抛射物数量 = 基础抛射物数量 + add_projectile
```

技能 A 原本基础数量是 1。

升级后，让 `add_projectile + 1`。

最终结果就是：

```text
1 + 1 = 2 个火球
```

这种方式的优点是简单直接，并且可以支持可变参数。

强化不需要替换技能，也不需要额外挂一个被动技能去间接释放火球。

技能释放时只需要根据自己的效果类型读取对应属性。

例如：

- 生成抛射物时读取额外抛射物数量
- 造成伤害时读取伤害加成
- 添加 Buff 时读取持续时间加成
- 搜索目标时读取范围加成

这样强化就变成了属性变化。

技能本身仍然按照原本流程执行，只是在执行到某个节点时读取对应参数。

## 共享属性的问题

直接把强化属性放在角色身上，会遇到一个问题。

如果升级只想增加技能 A 的火球数量，那么修改角色的 `add_projectile` 后，技能 B、技能 C、技能 D 也可能一起生效。

也就是说：

```text
角色共享属性会影响所有读取该属性的技能
```

有些强化确实应该这样。

例如“所有抛射物技能额外 +1 个抛射物”，就适合放在共享属性里。

但有些强化只应该影响特定技能。

例如：

```text
只有技能 A 额外 +1 个火球
```

这时就需要区分共享属性和私有属性。

## SkillModifier

可以引入一个技能修改器来管理技能强化属性。

它可以包含两类数据：

```text
共享属性：所有技能都可以读取
私有属性：只有指定技能可以读取
```

结构上可以简单表示为：

```csharp
public class SkillModifier
{
    /// <summary>
    /// 共享属性：所有技能都会读取的数据
    /// </summary>
    public Properties SharedProperties { get; }

    /// <summary>
    /// 私有属性：特定技能才会读取的数据，根据技能 ID 获取
    /// </summary>
    public Dictionary<int, Properties> PrivateProperties { get; }
}
```

共享属性用于全局强化。

例如：

```text
所有抛射物技能额外 +1 个抛射物
所有伤害技能伤害 +10%
所有 Buff 持续时间 +2 秒
```

私有属性用于单个技能强化。

例如：

```text
技能 A 额外 +1 个抛射物
技能 B 伤害 +20%
技能 C 冷却 -1 秒
```

技能释放时，可以同时读取两类属性。

例如技能 A 生成火球时：

```text
基础抛射物数量
+ 共享 add_projectile
+ 技能 A 私有 add_projectile
```

如果共享属性是 0，技能 A 私有属性是 1，那么技能 A 最终会释放 2 个火球。

技能 B、技能 C、技能 D 虽然也读取共享属性，但它们没有对应私有属性，因此仍然保持原本数量。

这样就解决了“强化只想作用于某个技能，但角色属性会污染所有技能”的问题。

## 对肉鸽技能的延伸

技能强化做到这一步后，就可以自然延伸到肉鸽类技能设计。

肉鸽技能设计的重点不一定是重新做一套技能系统。

更常见的思路是：

```text
基础技能
-> 获得强化
-> 修改技能参数
-> 形成不同构筑
```

例如同一个火球技能，可以通过不同强化变成：

- 更多火球
- 更高伤害
- 更大爆炸范围
- 命中后附加灼烧
- 每隔几次释放产生额外火球

其中一部分适合用技能属性实现。

另一部分适合用被动技能或触发器实现。

例如：

```text
火球数量 +1
```

更适合做成技能私有属性。

```text
每释放 3 次火球后，下一次额外爆炸
```

更适合做成被动技能或触发器。

因此，技能强化不是单一方案，而是要根据强化类型选择实现位置。

可以概括为：

```text
参数变化优先走技能属性
条件触发优先走被动技能或触发器
固定变体可以用替换技能
```

## 总结

技能强化可以从简单到复杂分成三种思路：

- 替换技能：简单直接，但只能支持预定义变种
- 被动技能：灵活，但容易让技能过程变得间接
- 技能属性：适合可变参数，适合作为强化的主要承载方式

如果强化只影响某个技能，单纯修改角色共享属性会污染其他技能。

因此，需要通过 SkillModifier 区分：

```text
SharedProperties：影响所有技能
PrivateProperties：只影响指定技能
```

这样既能支持全局强化，也能支持单个技能强化。

在这个基础上，肉鸽类技能设计就可以被理解为：

```text
不断给技能追加不同类型的强化
```

而不是重新设计一套完全独立的技能系统。
