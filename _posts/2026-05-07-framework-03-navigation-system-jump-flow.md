## 先给结论

系统跳转的意义，是解耦跳转发起方和目标系统。

在游戏客户端里，很多地方都会触发“去某个系统”：

- 主界面按钮
- 活动入口
- 奖励来源
- 红点点击
- 新手引导
- 弹窗按钮
- 聊天或提示链接

如果每个入口都直接打开目标界面，跳转逻辑会散落在各个 UI 和系统里。

更稳定的做法是让发起方只表达“我要去哪个系统”，至于目标系统对应哪个界面、是否需要先打开父级、是否需要关闭其他界面、是否需要走引导路径，都交给统一的跳转系统处理。

可以概括为：

```text
跳转发起方
-> 提出目标系统
-> 跳转系统解析目标
-> 按规则打开界面或引导路径
```

## 解决什么问题

没有统一跳转层时，常见问题是调用方知道太多细节。

例如一个按钮想进入某个系统，可能会直接知道：

- 目标界面类型
- 父级界面
- 打开顺序
- 是否关闭当前界面
- 是否需要切换页签
- 是否需要滚动到某个节点
- 是否需要等待目标界面初始化

这些信息一旦散落在各个入口里，后续维护会变得困难。

同一个系统可能有多个入口，如果每个入口都自己写一套打开逻辑，就容易出现行为不一致：

```text
主界面入口能正常进入
红点入口少打开了父界面
引导入口打开顺序不同
弹窗入口没有关闭无关界面
```

系统跳转要解决的就是这个问题：

> 入口不关心目标系统怎么打开，只关心要去哪个系统。

## 系统实现思路

系统跳转的第一步，是把“功能”抽象成一个系统模块。

一个系统模块通常需要描述：

- 系统标识
- 对应界面
- 父级系统
- 子级系统
- 是否解锁
- 是否已领取奖励
- 跳转方式
- 跳转参数

这样客户端就不再只面对一个个孤立界面，而是面对一棵系统结构。

例如：

```text
主界面
  -> 养成系统
     -> 装备界面
     -> 技能界面
  -> 活动系统
     -> 活动列表
     -> 活动详情
```

当目标是一个子系统时，跳转系统可以根据父子关系推导出完整路径。

这比直接打开目标界面更稳定，因为很多子界面依赖父界面的容器、页签或上下文。

## 跳转实现思路

跳转实现可以拆成两部分：

```text
系统解析
-> 按路径逐步跳转
```

系统解析负责回答：

- 目标系统是否存在
- 目标系统是否解锁
- 是否有父级系统
- 需要先打开哪些父级
- 是否需要关闭无关界面
- 使用哪种跳转方式

一个常规跳转流程可以表示为：

```text
请求跳转到目标系统
-> 查找目标模块
-> 检查解锁状态
-> 计算父级路径
-> 关闭无关界面
-> 按父到子的顺序打开
-> 执行目标跳转
-> 回调跳转完成
```

这样入口只需要传入目标系统，跳转系统负责处理路径和细节。

## 跳转系统的两种方式

系统跳转本身可以分成两种方式：

```text
按系统路径跳转系统
直接打开系统
```

这两种方式解决的是“目标系统应该如何进入”的问题。

### 按系统路径跳转系统

按系统路径跳转，适合依赖系统结构的内容。

例如目标系统藏在多层界面下：

```text
主界面
-> 功能入口
-> 子系统列表
-> 目标系统
```

这种情况下，跳转系统不能只打开最终界面，而是要根据系统结构找到父级路径，再按路径逐步进入。

这样做的价值是：目标系统不会脱离它所属的界面结构被孤立打开。

一个子系统往往依赖父级界面提供容器、页签、上下文或初始状态。如果直接打开子系统，界面可能能显示，但上下文不完整，后续行为就容易不一致。

因此，按系统路径跳转可以理解为：

```text
目标不是打开一个界面
而是进入一条系统路径
```

### 直接打开系统

直接打开系统，适合不依赖系统路径的通用内容。

例如：

```text
道具弹窗
奖励预览
通用说明
确认弹窗
```

这类系统或界面通常有几个特点：

- 不依赖父级路径
- 不改变当前系统结构
- 可以在任何界面上方展示
- 关闭后回到原来的上下文

因此，系统跳转不应该只有“按路径进入系统”一种方式。

更合理的做法是：

```text
结构型系统
-> 按系统路径跳转

通用型系统
-> 直接打开系统
```

## 跳转实现的两种方式

上面讲的是跳转系统的进入方式。

真正执行跳转时，还需要有具体的实现方式。

这里可以把实现封装成 Jumper。

Jumper 的意义是把“跳转系统如何解析目标”和“最终如何执行跳转”拆开。

跳转系统负责找到目标模块、计算路径、判断解锁状态；Jumper 负责执行具体跳转动作。

这里只需要关注两种实现：

```text
JumpToUI：直接打开系统界面
JumpToPath：点击界面的某个控件
```

### JumpToUI

JumpToUI 解决的是“直接打开某个界面”。

它适合目标界面已经足够明确的情况。

例如：

```text
打开道具弹窗
打开奖励预览
打开某个系统主界面
```

这种实现方式不关心界面内部的具体控件，只负责把目标界面打开。

### JumpToPath

JumpToPath 解决的是“进入界面后点击某个控件”。

它适合目标不是一个界面，而是界面内部的某个入口、按钮、页签或节点。

例如：

```text
打开系统主界面
-> 切到指定页签
-> 滚动到指定列表项
-> 定位到某个按钮或节点
```

这种实现方式适合新手引导、红点定位、奖励来源跳转等场景。

因为这些入口往往不是简单地“打开界面”就结束，而是要把玩家带到界面内部的某个具体控件。

可以理解为：

```text
JumpToUI：打开界面
JumpToPath：点击控件
```

## 额外的好处

统一系统跳转后，很多后续功能都会更容易接入。

### 新手引导

新手引导需要知道目标系统在哪里，以及如何让玩家一步步到达。

如果系统跳转已经有模块结构和路径关系，引导就可以复用这些信息，而不是重新维护一套入口路径。

### 红点系统

红点通常不只是显示提示，还需要点击后跳到对应系统。

如果红点只绑定一个系统标识，那么点击红点时就可以直接交给跳转系统处理。

这样红点不需要知道目标界面怎么打开。

### 奖励来源

很多奖励会展示“前往获取”。

如果奖励来源绑定的是系统模块，而不是具体界面，那么奖励入口就可以复用统一跳转。

### 功能解锁

系统模块本身可以带解锁状态。

跳转前先判断目标是否解锁，就可以避免未解锁系统被错误打开，也能统一处理提示文案。

## 总结

系统跳转的核心价值，是把“去某个系统”从具体 UI 打开逻辑中抽象出来。

可以概括为：

```text
入口只表达目标
系统模块描述结构
跳转系统解析路径
跳转执行器进入目标
```

这样做能让跳转发起方和目标系统解耦。

按钮、红点、引导、奖励来源、弹窗都可以使用同一套跳转语义，而不是各自维护一份打开界面的逻辑。

因此，系统跳转不仅是一个 UI 打开工具，更是后续新手引导、红点系统、功能解锁和来源跳转等通用能力的基础。
