## 先给结论

回合制战斗的核心思路是战报驱动。

也就是说，战斗结果已经提前计算完成，客户端不负责决定胜负、伤害、治疗、Buff 等结果。

客户端的主要职责是：

```text
读取战报
-> 按顺序播放战斗过程
```

在这个基础上，再通过命令序列把每一次行动拆成可执行、可暂停、可继续的播放流程。

可以概括为：

```text
战报决定结果
命令序列负责播放
```

## 战报驱动

回合制战斗天然适合战报驱动。

因为它本身就是一段离散流程：

```text
第 1 回合
-> A 行动
-> B 行动
-> 触发被动
-> 进入下一回合
```

每一次行动都可以被记录下来。

一条行动通常包含：

- 行动者
- 目标
- 释放技能
- 行动类型
- 战斗事件列表

其中行动描述的是“谁做了什么”，战斗事件描述的是“这件事产生了什么结果”。

例如：

```text
行动：角色 A 对角色 B 释放技能
事件：角色 B 受到伤害
事件：角色 B 获得 Buff
事件：角色 A 怒气变化
```

这样设计后，结算和表现就被拆开了。

战报负责记录结果，客户端负责消费结果。

客户端播放时，只需要按战报顺序推进：

```text
读取行动
-> 播放行动表现
-> 消费行动中的事件
-> 更新当前状态
-> 进入下一条行动
```

这种方式的好处是结果稳定。

同一份战报无论播放多少次，都应该得到同样的战斗过程和最终状态。

这对跳过战斗、战报复盘、倍速播放、断线恢复都很重要。

## 命令序列

战报中的行动只是数据。

真正播放时，需要把行动转成命令。

例如：

```text
主动攻击行动
-> 主动攻击命令
```

```text
被动触发行动
-> 被动效果命令
```

命令的职责是组织这一段行动的播放过程。

主动攻击命令可能会做这些事：

- 显示行动类型
- 播放技能动作
- 移动到目标附近
- 在关键帧触发战斗事件
- 播放受击、飘字、死亡等表现
- 行动结束后回到默认状态

被动效果命令通常更简单：

- 直接消费战斗事件
- 播放对应表现
- 等待短暂间隔

命令序列则负责把这些命令按顺序执行。

可以抽象为：

```text
Command 1
-> Command 2
-> Command 3
-> ...
-> 战斗结束
```

每个命令只需要关注自己的生命周期：

```text
未执行
执行中
已完成
```

命令序列只需要判断当前命令是否完成。

当前命令完成后，再执行下一个命令。

这样回合制战斗的流程控制就会变得很清晰。

暂停战斗时，停止命令序列自动推进。

恢复战斗时，从当前命令继续向后执行。

需要重播某个行动时，也可以把命令序列定位到指定位置重新播放。

## 两者的关系

战报驱动解决的是“结果从哪里来”。

命令序列解决的是“过程怎么播放”。

两者的职责不同：

```text
战报：描述行动和结果
命令：组织单次行动的播放
命令序列：按顺序推进所有命令
```

例如一条主动攻击行动，可以被拆成：

```text
战报行动
-> 构建主动攻击命令
-> 播放技能动作
-> 在动作关键帧消费战斗事件
-> 更新状态并播放表现
-> 命令完成
```

如果是被动触发行动，则可以被拆成：

```text
战报行动
-> 构建被动效果命令
-> 消费战斗事件
-> 播放对应表现
-> 命令完成
```

也就是说，战报不关心表现怎么播，命令也不重新计算战斗结果。

它们之间只通过行动数据和战斗事件连接。

## 总结

回合制战斗可以先抓住两个核心点：

- 战报驱动
- 命令序列

战报驱动让战斗结果稳定。

命令序列让播放过程可控。

可以概括为：

```text
读取战报
-> 将行动构建为命令
-> 按顺序执行命令
-> 命令中消费战斗事件
-> 推进状态并播放表现
-> 战斗结束
```

只要这两层边界清楚，后续再扩展主动攻击、被动触发、关键帧、多段伤害、抛射物命中、跳过战斗和战报复盘，都会有明确的位置。
