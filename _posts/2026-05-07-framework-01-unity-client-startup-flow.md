## 先给结论

启动流程的意义，是在进入游戏主逻辑前，保证所有基础系统已经初始化完成。

这里的基础系统通常包括：

- 运行环境
- 常驻对象
- 资源系统
- 配置系统
- 本地化系统
- 启动 UI
- 逻辑程序集
- 其他主逻辑依赖的公共服务

如果这些前置条件没有准备好，主逻辑一旦开始运行，就会在资源加载、配置读取、界面打开、系统初始化等地方出现不稳定行为。

因此，启动流程不是单纯“进入游戏前跑一堆初始化”，而是负责建立一条明确的前置条件链路：

```text
基础系统准备完成
-> 主逻辑入口执行
-> 游戏正式开始
```

## 启动流程的设计

启动流程更适合被设计成一组阶段，而不是一个不断膨胀的入口函数。

每个阶段只负责一类问题：

```text
当前阶段做什么
完成后进入哪个阶段
失败时如何处理
是否允许跳过
是否需要等待异步结果
```

这样的设计有几个好处。

第一，依赖顺序更清楚。

资源系统准备好之后，才能加载配置、UI、程序集等内容；配置系统准备好之后，主逻辑中的系统才可以安全读取数据。

第二，问题定位更容易。

如果启动卡住，可以直接判断卡在哪个阶段，而不是在一大段初始化代码里排查。

第三，扩展更稳定。

后续如果要加入热更新、公告、隐私协议、资源预加载、账号初始化等流程，只需要把它们放到合适的阶段或新增阶段，而不是打乱已有启动逻辑。

因此，一个比较稳定的启动设计可以概括为：

```text
用阶段管理启动过程
用状态切换推进流程
用启动 UI 反馈当前进度
在所有基础系统完成后再进入主逻辑
```

## 常规启动流程

一个常规客户端启动流程可以拆成：

```text
初始化运行环境
-> 初始化常驻对象
-> 初始化资源系统
-> 检查资源状态
-> 预加载基础资源
-> 加载配置
-> 加载逻辑程序集
-> 执行主逻辑入口
-> 启动结束
```

### 初始化运行环境

这一阶段通常会处理帧率、后台运行、屏幕常亮、时间缩放等基础设置。

它的目标是让客户端处于一个稳定的运行状态。

### 初始化常驻对象

一些对象需要跨场景保留，例如主相机、UI 根节点、事件系统或启动流程对象本身。

这些对象如果在切场景时被销毁，后续 UI、输入或流程推进就可能出现异常。

### 初始化资源系统

资源系统是很多模块的基础。

配置、UI、音频、Prefab、程序集等内容都可能依赖资源系统加载，因此资源系统通常需要放在比较靠前的位置。

### 检查资源状态

资源系统初始化后，可以检查当前资源是否满足运行条件。

如果涉及热更新，这一步会判断是否需要更新资源。但热更新本身会包含 Project 存放规则、代码和程序集组织、资源包规则等更多内容，适合后续单独展开。

在启动流程总览里，只需要把它看成一个资源状态检查阶段。

### 预加载基础资源

预加载用于提前准备主逻辑马上会用到的资源。

预加载不应该无限扩大，只应该放启动后立刻需要的内容，否则会拖慢进入游戏的速度。

### 加载配置

配置系统应该在主逻辑入口之前完成。

这样主逻辑中的系统初始化时，就可以直接读取配置，而不是每个系统都自己处理异步加载或空数据保护。

### 加载逻辑程序集

如果项目支持逻辑热更，主逻辑可能需要在运行时加载程序集。

这一阶段的目标是找到并准备好真正的游戏逻辑入口。

### 执行主逻辑入口

当资源、配置、程序集和基础服务都准备好之后，才执行主逻辑入口。

此时主逻辑可以假设基础环境已经就绪，不需要在每个系统中重复判断“框架是否已经准备好”。

## 总结

启动流程的核心价值，是把进入游戏前的前置条件整理成一条可控链路。

它不是为了让入口更复杂，而是为了让主逻辑更简单。

一个好的启动流程应该做到：

- 阶段清晰
- 依赖明确
- 失败可定位
- 进度可反馈
- 主逻辑入口足够干净

因此，启动流程的设计重点可以概括为：

> 在进入游戏主逻辑之前，用明确的阶段保证所有基础系统已经初始化完成。
