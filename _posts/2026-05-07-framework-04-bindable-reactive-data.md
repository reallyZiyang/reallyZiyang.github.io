## 先给结论

Bindable 的意义，是通过响应式结构解耦界面和数据。

传统写法里，数据变化后往往需要手动刷新界面：

```text
数据变化
-> 找到对应 UI
-> 手动设置文本、图片、显隐、按钮状态
```

这种方式在界面简单时没有问题，但当状态来源变多、界面数量变多、刷新条件变复杂时，很容易出现漏刷、重复刷、刷新时机不一致的问题。

Bindable 的思路是反过来：

```text
UI 绑定数据
-> 数据变化
-> UI 自动收到通知
-> UI 根据新值刷新表现
```

也就是说，UI 不再需要到处追着数据刷新，而是让数据变化主动通知 UI。

## 解决什么问题

游戏 UI 中有大量状态并不是一次性展示，而是会在运行过程中不断变化。

例如：

- 按钮是否可点击
- 功能是否解锁
- 红点是否显示
- 奖励是否已领取
- 资源数量是否变化
- 列表中是否新增或删除元素
- 某个 UI 节点是否需要显示

如果每次状态变化都手动调用界面刷新，代码很容易变成：

```text
请求返回时刷新一次
按钮点击后刷新一次
打开界面时刷新一次
红点变化时刷新一次
其他系统变化时再刷新一次
```

问题不在于刷新本身，而在于刷新关系会变得分散。

Bindable 解决的是“谁来通知 UI 刷新”的问题。

它让状态本身具备通知能力，UI 只需要在合适的生命周期内完成绑定。

## Bindable 的实现思路

Bindable 可以理解为一个带变化通知的数据包装。

普通字段只保存值：

```text
bool unlocked
int count
string name
```

Bindable 保存值的同时，还能在值变化时通知监听者：

```text
Bindable<bool> unlocked
Bindable<int> count
Bindable<string> name
```

它的核心流程可以简化成：

```text
设置新值
-> 判断是否真的变化
-> 保存新值
-> 通知所有监听者
```

这样 UI 只需要监听这个值：

```text
功能解锁状态变化
-> 按钮显隐刷新

资源数量变化
-> 文本刷新

红点状态变化
-> 红点节点刷新
```

Bindable 本身不关心 UI 长什么样，也不关心数据来自哪里。

它只负责一件事：

> 当数据变化时，把变化通知出去。

## 集合也需要响应式

单个值可以响应变化，集合也需要响应变化。

因为游戏 UI 里大量内容都是列表或字典结构。

例如：

- 背包列表
- 任务列表
- 奖励列表
- 系统入口列表
- 红点节点表
- 导航模块表

如果集合只提供“整体变化”通知，那么每次变化都可能需要重建整个列表。

更细的做法是让集合能通知具体变化：

```text
元素新增
元素删除
元素修改
元素移动
元素交换
```

这样 UI 可以按变化类型做增量刷新。

例如新增一个奖励项时，只创建一个新节点；删除一个任务时，只移除对应节点；排序变化时，只调整显示顺序。

这种设计可以让 UI 列表更容易和数据结构保持一致。

## 生命周期绑定

响应式结构最容易出问题的地方，是生命周期。

因为 UI 通常是临时存在的。

例如：

```text
打开界面
-> 绑定数据
-> 数据变化时刷新 UI
-> 关闭界面
```

如果界面关闭后没有解绑，数据再次变化时，回调仍然会被触发。

这会带来几个问题：

- 访问已经销毁的 UI 对象
- 出现空引用或 Unity 假空对象
- 重复绑定导致多次刷新
- 关闭的界面仍然响应数据变化
- 内存和事件引用无法释放

因此，Bindable 不能只解决“如何通知”，还必须解决“什么时候解绑”。

更稳定的方式是把绑定关系挂到 UI 生命周期上：

```text
UI 创建
-> 建立绑定

UI 销毁
-> 自动释放绑定
```

这样 UI 不需要在每个地方手写解绑逻辑，也能避免响应式回调比界面活得更久。

## Bindable 和 UI 的边界

Bindable 不应该让数据层知道 UI。

正确的方向是：

```text
数据层只负责改变 Bindable 的值
UI 层负责绑定 Bindable 并刷新表现
```

例如一个功能是否解锁，数据层只需要维护解锁状态。

至于这个状态在界面上表现为按钮可点、灰色遮罩、红点隐藏，还是入口显示，都应该由 UI 绑定逻辑决定。

这样可以避免数据层反过来依赖具体界面。

## 总结

Bindable 的核心价值，是让数据变化具备通知能力。

它解决的不是复杂业务逻辑，而是 UI 和数据之间的刷新关系。

可以概括为：

```text
数据用 Bindable 表达
UI 绑定 Bindable
数据变化自动通知 UI
UI 生命周期结束时释放绑定
```

因此，Bindable 的设计重点不只是“值变化时触发回调”，还包括集合变化通知和生命周期解绑。

只有把生命周期绑定处理好，响应式结构才不会从“减少刷新代码”变成“制造隐藏引用和重复回调”的问题。
