## 先给结论

Skill 是技能效果的流程性描述。

相比 Effect 的一次性执行、Buff 的持续性状态，Skill 更接近一段具象化的行为流程。它通常会包含动作、目标、前后摇、关键帧、索敌和效果触发等内容。

因此，Skill 的难点不只是“能不能触发效果”，而是：

> 如何用数据描述一段具象化的技能流程，并提前规划技能复杂度边界。

## Skill 的描述通常是具象的

当讨论一个技能时，常见描述通常不是抽象字段，而是一段比较具象的行为过程。

例如：

```text
冲向棋盘中央，召唤武魂真身将所有敌方拉至中心，本体抓取敌人后跃起猛砸，造成击倒效果。
```

```text
吞噬目标造成魔法伤害，并永久提升自身生命值；若击杀目标，则叠加更多生命值。
```

```text
呼叫空中炮艇盘旋，随机投掷炸弹降低护甲魔抗，随后精准射击造成额外伤害。
```

这些描述来自实际游戏中的技能文本，可以看到 Skill 在表达上通常非常具象。

它不像 Effect 那样只描述一次结果，也不像 Buff 那样描述持续状态，而是在描述一段完整的行为过程。

因此，实现 Skill 的核心问题是：

```text
如何把一段具象化的技能描述，拆成可配置、可执行、可维护的数据流程。
```

## 常见数据和字段

一个常规 Skill 通常会包含一些基础数据。

常见数据包括：

- 施法者
- 施法目标
- 目标数量
- 冷却时间
- 消耗
- 技能等级

常见字段包括：

- 索敌机制
- 施法动作
- 施法前摇
- 施法后摇
- 效果触发关键帧
- 能否被打断
- 打断后如何处理

这些字段并不一定每个技能都需要，但它们共同描述了一个技能从开始到结束的流程。

## Skill 和 Buff 的区别

Buff 在实现上相对通用。

不管是哪种类型的游戏，Buff 通常都可以围绕时间和生命周期来设计：

```text
添加
-> 持续
-> Tick
-> 移除
```

而 Skill 的实现形态会更加多样。

有的技能依赖动作关键帧，有的技能依赖弹道，有的技能依赖输入节奏，有的技能几乎不需要动作，甚至只需要定期自动触发。

所以 Skill 的复杂度和游戏类型关系很大。

为了控制讨论范围，这里只讨论一种最常见的技能思路：

> 技能就是角色播放一个动作，并在动作流程中产生一些效果。

从实现角度可以进一步描述为：

```text
角色释放技能
-> 播放对应动作
-> 前摇结束
-> 通过索敌机制选择目标
-> 在关键帧触发 Effect
-> 动作结束
-> 技能结束
```

## Skill 依赖动作流程触发效果

Buff 通常依赖时间推进来触发效果。

例如：

```text
每 1 秒触发一次 DamageEffect
持续 5 秒后移除
```

而常规 Skill 更多依赖动作流程来触发效果。

例如：

```text
播放攻击动作
-> 第 0.4 秒触发索敌
-> 第 0.45 秒触发 DamageEffect
-> 第 0.8 秒允许进入下一个状态
```

为了追求演出效果，Skill 往往需要在动作中插入关键帧，精确控制效果触发时间。

这些关键帧可以用于：

- 触发伤害
- 生成抛射物
- 添加 Buff
- 播放特效
- 产生位移
- 锁定目标
- 允许取消后摇

因此，常规 Skill 的核心不是简单地“释放后立刻触发效果”，而是用动作流程驱动效果触发。

## Skill 的最大难点：复杂度规划

Skill 在技能系统中往往是复杂度最高的部分。

最主要的原因是：不同游戏对 Skill 的要求差异非常大。

例如格斗游戏中的技能，可能需要考虑：

- 搓招输入
- 联网同步
- 极高精度的攻击判定
- 帧数据
- 取消窗口
- 受击硬直

而类吸血鬼幸存者的技能，可能更关注：

- 无动作释放
- 自动触发
- 大量同屏目标
- 大量弹幕或范围效果
- 单机环境下的性能控制

这两类 Skill 的设计目标完全不同，实现方式也不应该相同。

如果一个系统同时追求格斗游戏的高精度判定，又追求类吸血鬼幸存者的大量同屏目标和高频触发，复杂度会快速上升。

但如果一开始就明确技能边界，只保留当前项目真正需要的特性，那么实现难度就是可控的。

因此，Skill 的设计重点不只是字段如何配置，而是要先明确项目需要什么级别的技能复杂度。

## 技能边界需要提前明确

在设计 Skill 之前，至少需要先明确一些边界：

- 是否需要高精度帧判定
- 是否需要联网同步
- 是否允许技能被打断
- 是否需要取消前后摇
- 是否需要弹道和飞行时间
- 是否需要大量同屏目标
- 是否需要多段关键帧
- 是否需要复杂目标选择
- 是否需要技能过程中改变目标

这些问题决定了 Skill 系统的复杂度上限。

如果边界不清晰，系统很容易在后续需求中不断补丁式扩展，最后变成一个既难维护又难复用的流程集合。

## 常规技能流程

在边界明确之后，常规 Skill 的流程可以保持相对简单。

一个基础流程可以抽象为：

```text
请求释放技能
-> 判断释放条件
-> 锁定或选择目标
-> 播放施法动作
-> 进入前摇
-> 到达关键帧
-> 触发 Effect
-> 进入后摇
-> 技能结束
```

这里的重点是：Skill 负责组织流程，Effect 负责执行结果。

例如：

```text
Skill 配置：
- 施法动作：Attack_01
- 目标规则：选择最近的 1 个敌人
- 触发时间：0.45 秒
- 触发效果：DamageEffect

运行时：
播放 Attack_01
-> 0.45 秒时索敌
-> 对目标执行 DamageEffect
```

这样 Skill 不需要直接写死扣血逻辑，而是只需要在合适的时间点触发对应 Effect。

## 总结

Skill 是技能效果的流程性描述。

它的难点不只是触发某个 Effect，而是如何把具象化的技能文本拆成一段可执行的数据流程。

对于常规技能来说，一种稳定的实现思路是：

```text
Skill 负责动作流程
动作流程提供关键帧
关键帧触发 Effect
Effect 对目标产生具体结果
```

Skill 系统真正需要优先规划的是复杂度边界。

如果项目只需要常规动作驱动技能，就不应该过早引入过重的帧判定、联网同步、复杂取消窗口或大规模弹幕机制。

反过来，如果项目从一开始就需要这些能力，就必须在系统设计阶段提前纳入，而不是等需求出现后再临时补充。

因此，Skill 的设计重点可以概括为：

> 先确定技能复杂度边界，再用数据描述技能流程，最后通过关键帧触发 Effect。
