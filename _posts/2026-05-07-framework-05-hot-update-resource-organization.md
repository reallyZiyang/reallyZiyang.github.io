## 先给结论

游戏热更新框架的核心，是区分项目中“不变的部分”和“变化的部分”。

不变的部分保留在包体和工程基础设施里，变化的部分通过热更新资源包下发。

可以概括为：

```text
不变部分
-> 支撑游戏启动和热更新能力

变化部分
-> 通过资源包更新
```

在这套思路里，YooAsset 主要负责资源更新，HybridCLR 主要负责逻辑代码更新。

游戏资源和逻辑代码最终都可以作为可更新内容被打进资源包。启动流程中检测是否有更新，若有更新则下载更新内容，并在启动流程后段加载逻辑程序集。

## 不变和变化的边界

热更新设计首先要明确边界。

哪些内容应该跟随包体发布，哪些内容应该可以被远端更新。

### 不变的部分

不变的部分通常包括：

- 项目插件
- 项目设置
- 编辑器资源和代码
- 启动流程
- 热更新基础设施

这些内容不适合频繁变化。

它们更像是游戏能够启动和执行热更新的底座。如果底座本身都依赖热更新，启动过程就会变得不稳定。

因此，启动流程、资源系统、程序集加载能力、基础设置等内容应该尽量保留在包体内。

### 变化的部分

变化的部分通常包括：

- 游戏美术资源
- 配置
- 音效
- UI 资源
- 场景资源
- 玩法资源
- 游戏逻辑代码

这些内容会随着版本迭代频繁变化。

如果每次修改资源或逻辑都需要重新发整包，更新成本会很高。

因此，这些内容更适合进入热更新资源体系。

## YooAsset 和 HybridCLR 的职责

YooAsset 和 HybridCLR 解决的是两个不同问题。

### YooAsset：资源更新

YooAsset 主要负责资源包管理。

它可以把游戏资源按 Package 组织起来，并在启动或运行过程中检查版本、下载资源、加载资源。

在热更新框架中，它承载的是：

```text
资源如何收集
资源如何分包
资源如何检查版本
资源如何下载
资源如何加载
```

美术、配置、音效、Prefab、场景等内容，都可以通过 YooAsset 的资源包体系进行管理。

### HybridCLR：逻辑代码更新

HybridCLR 主要负责逻辑代码热更新。

它让部分游戏逻辑可以在运行时通过程序集形式加载，而不是完全固定在包体代码中。

在热更新框架中，它承载的是：

```text
逻辑代码如何作为更新内容下发
启动时如何加载程序集
主逻辑入口如何执行
```

因此，YooAsset 和 HybridCLR 的关系可以理解为：

```text
YooAsset 负责“资源怎么更新”
HybridCLR 负责“代码怎么更新”
```

而代码程序集本身，也可以作为资源包中的一种资源被下载和加载。

## 启动流程中的热更新位置

热更新不应该独立于启动流程之外。

更合理的做法是把它放进启动流程中，作为进入主逻辑之前的一个阶段。

常规流程可以表示为：

```text
启动游戏
-> 初始化资源系统
-> 检查资源包版本
-> 下载需要更新的资源包
-> 加载核心资源
-> 加载逻辑程序集
-> 执行主逻辑入口
```

这里的关键点是：主逻辑入口应该在资源和代码都准备好之后再执行。

否则主逻辑可能会访问到旧资源、缺失配置或未加载的程序集。

## Package 的资源编排

YooAsset 通过 Package 来组织资源。

Package 的意义不是简单地把资源打包，而是给资源更新和加载建立边界。

一个项目可以按资源的重要程度和使用场景拆分 Package。

例如：

```text
核心资源 Package
拓展商业化资源 Package
拓展玩法资源 Package
拓展场景资源 Package
其他按需资源 Package
```

### 核心资源 Package

核心资源是游戏运行所需的最小资源集合。

它应该包含启动后立刻需要的内容，例如：

- 基础配置
- 基础 UI
- 基础字体或图集
- 主逻辑程序集
- 进入游戏前必须存在的公共资源

启动流程中应该优先加载核心资源 Package。

这样可以保证游戏主逻辑能够启动，同时避免一开始就下载所有资源。

### 拓展资源 Package

拓展资源可以按使用场景拆分。

例如：

```text
商业化资源
-> 商店、礼包、活动展示等相关资源

玩法资源
-> 某个玩法模块使用的资源

场景资源
-> 大型场景、地图、关卡资源
```

这些资源不一定要在启动时全部下载。

更合理的方式是按需加载：

```text
用户主动进入某个玩法
-> 检查该玩法资源是否已下载
-> 若未下载则下载
-> 下载完成后进入玩法
```

或者：

```text
用户主动下载拓展内容
-> 下载对应 Package
-> 后续进入时直接使用
```

## 启动只加载核心资源

启动阶段最重要的是尽快让游戏进入可运行状态。

因此启动流程不应该默认加载所有 Package。

更合理的策略是：

```text
启动阶段
-> 加载核心资源 Package

运行阶段
-> 按需加载拓展 Package
```

这样可以降低首启成本，也能减少用户进入游戏前的等待时间。

拓展资源可以在用户真正需要时再加载，例如进入玩法前下载、打开商业化界面前下载、进入大场景前下载。

## 总结

热更新资源编排的核心不是“把所有东西都做成可更新”，而是先划清边界。

可以概括为：

```text
启动和热更新基础设施保持稳定
游戏资源和逻辑代码作为变化内容进入资源包
启动流程只保证核心资源可用
拓展资源按需下载和加载
```

YooAsset 负责资源包管理，HybridCLR 负责逻辑代码更新。

二者结合后，资源和代码都可以进入热更新体系，但启动流程仍然要保持清晰：先保证核心资源和主逻辑程序集可用，再进入游戏主逻辑。
